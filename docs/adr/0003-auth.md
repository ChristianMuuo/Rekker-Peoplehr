# ADR 0003: Authentication, Sessions, CSRF & Admin MFA

**Date:** 2026-11-25  
**Status:** Proposed (Phase 0)

---

## Context

Currently, `artifacts/peopleos/src/auth.tsx` and `artifacts/api-server/src/middlewares/peopleosAccess.ts` operate in two divergent modes:

1. **Demo mode (`PEOPLEOS_AUTH_MODE=demo`)**: The browser stores `'admin' | 'manager' | 'employee'` in `localStorage` (`rekker_peopleos_auth_user`) and sends spoofable headers (`x-peopleos-user-id`, `x-peopleos-role`, `x-peopleos-employee-id`) with **no password verification, no cryptographic session, no CSRF protection, and no MFA**.
2. **Clerk mode (`PEOPLEOS_AUTH_MODE=clerk`)**: Requires paid/configured `CLERK_SECRET_KEY` and `VITE_CLERK_PUBLISHABLE_KEY`; unused on the live Vercel demo, which therefore drops back to one-click demo role buttons (`DemoAdmin`, `DemoManager`, `DemoEmployee`).

Client feedback explicitly asks for **real login** and **real backend auth/tests**, and Workstream C specifies:
> *"real login (argon2id passwords or a managed provider, justified in the ADR), httpOnly + Secure + SameSite cookies, CSRF protection, login rate limiting and lockout, password reset, TOTP MFA required for admin roles, session expiry and revocation."*

---

## Options Considered

| Option | Description | Trade-offs |
|---|---|---|
| **A. First-Party Cookie Session Auth (`argon2id` + DB Sessions + TOTP MFA + CSRF)** *(Recommended)* | Implement first-party authentication in `api-server` + `lib/db`: `users` table with `argon2id` password hashes, `sessions` table with opaque cryptographic session tokens stored in `httpOnly; Secure; SameSite=Lax` cookies, double-submit/synchronizer CSRF token on state-changing requests, sliding/absolute expiry + revocation, login rate limiting & account lockout, password-reset token flow (behind email provider / dev-log transport), and mandatory RFC 6238 TOTP MFA (plus backup codes) for admin roles (`hr_admin`, `system_admin`, `finance_manager`, `hr_director`). Keep Clerk as optional enterprise SSO adapter behind feature flag if configured later. | **Pros:** Works identically in local dev, CI, Playwright E2E, and hosted Vercel+API demo with **zero external SaaS keys or Clerk domain restrictions**; enforces `httpOnly` + `Secure` + `SameSite` cookies, CSRF, lockout, and admin TOTP natively; deterministic seeded demo credentials allow reviewers and E2E tests to log in as real distinct users (employee, manager, HR admin). **Cons:** We own password hashing, session storage, and TOTP verification logic (must use vetted Node `crypto` / `argon2` + `otplib` or standard RFC 6238/4226 implementation and thorough security tests). |
| **B. Clerk Managed Auth Exclusively** | Require `CLERK_SECRET_KEY` + `VITE_CLERK_PUBLISHABLE_KEY` across all environments and delete demo auth. | **Pros:** Offloads UI, password reset, and TOTP screens to Clerk. **Cons:** Requires live Clerk application keys tied to exact Vercel/custom domains; breaks offline/CI Playwright E2E without brittle Clerk test-token workarounds; couples demo credentials to external Clerk tenant state; does not align well with custom demo passcode gating or self-contained Postgres session revocation. |

---

## Proposed Decision

Adopt **Option A (First-Party `argon2id` + `httpOnly` Cookie Session Auth with Mandatory Admin TOTP MFA and CSRF Protection)** as the primary authentication architecture, keeping optional Clerk bearer-token verification isolated behind an explicit opt-in flag (`PEOPLEOS_AUTH_MODE=clerk`) if needed later.

1. **Password Hashing:** `argon2id` (`@node-rs/argon2` or `argon2` package) with standard OWASP memory/time parameters; never store plaintext passwords or allow header-based role spoofing (`x-peopleos-role` removed from live auth paths).
2. **Sessions:** DB-backed `user_sessions` table (`id`, `user_id`, `organization_id`, `token_hash`, `mfa_verified_at`, `expires_at`, `revoked_at`, `ip`, `user_agent`). Delivered exclusively via `httpOnly`, `SameSite=Lax`, `Secure` (in HTTPS/prod) cookie via same-origin `/api` proxy.
3. **CSRF Protection:** `Origin`/`Referer` verification + signed/session-bound `X-CSRF-Token` header required on all `POST`/`PATCH`/`PUT`/`DELETE` routes (except public login/passcode endpoints which check `Origin`).
4. **Rate Limiting & Lockout:** Per-IP and per-account sliding-window login rate limiter + temporary lockout after consecutive failed attempts, recorded in `audit_log`.
5. **Admin TOTP MFA:** Roles with privileged access (`system_admin`, `hr_admin`, `hr_director`, `finance_manager`) must enroll and verify a 6-digit TOTP code before privileged session access is granted.
6. **Public Demo Gate:** Server-side demo invite/passcode middleware issuing an `httpOnly` gate cookie (`DEMO_PASSCODE` / per-viewer revocable invite codes), completely independent of client-side JS.
7. **Seeded Demo Users:** Standard non-admin & admin synthetic accounts (`@rekker-demo.invalid`) with documented demo credentials shown clearly on the demo login screen (for gated demo environments only) so evaluators can test real login across Employee, Manager, and HR Admin roles.

---

## Consequences

- Real end-to-end authentication works in local dev, GitHub Actions CI, Playwright E2E, and the live Vercel deployment with zero third-party auth outages or unverified headers.
- Header-based role spoofing (`x-peopleos-role`) is eliminated from live routes (existing unit tests using legacy headers will be updated or migrated cleanly to session auth in Workstream C).
- Adds dependencies `@node-rs/argon2` (or `argon2`) and `otpauth` (or `otplib`) + `qrcode` for TOTP setup.
